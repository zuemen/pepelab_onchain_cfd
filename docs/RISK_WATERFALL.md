## 1. 誰是對手方

- **永續 CFD**：沒有獨立的做市商或 LP 對手方。所有交易者的保證金集中在 exchange 合約的 USDC 餘額，
  這個資金池就是所有部位的對手方。贏家的獲利只是記入 `freeMargin`，提領時由 exchange 自己的餘額支付；
  餘額不足時提領會 revert，**不會**自動向保險金庫撥款。
- **保險金庫（InsuranceVault）**：由 LP 存入 USDC 取得份額（pIV）。只在「虧損超過保證金」時介入。
  LP 提領沒有鎖倉期。
- **代幣化配置（AssetVaultV2）**：金庫是每一個多頭的對手方，見第 5 節。

## 2. 現行部署版：損失吸收順序

以下以單一部位為單位（逐倉）。

### 2.1 自願平倉、虧損大於保證金

1. **交易者保證金**：`平倉金額 = 保證金 + 損益 − 交易費 − 借貸費 − funding`。若小於 0，交易者拿回 0，
   差額成為缺口。交易者**不會**被倒扣其他 `freeMargin`（逐倉下的負餘額保護）。
2. **保險金庫**：`撥款 = min(缺口, 金庫總資產)`，由 `InsuranceVault.bailout` 撥回 exchange。
   沒有單次撥款上限，金庫可以被撥到 0。
3. **ADL（自動減倉）**：金庫不足時，對同一資產、反方向、目前有獲利的部位，依建立順序掃描
   （最多 128 筆），逐筆以市價強制平倉，並從其**獲利**扣除缺口（haircut），本金不動。
   發出 `AutoDeleveraged` 事件。
4. **壞帳事件**：仍未覆蓋的部分發出 `BadDebt(positionId, asset, uncovered)`。
   此時資金池帳面上短少，**沒有後續自動補足機制**；是否由營運方注資，屬於政策決定。

另有一個「bailout floor」：只有在金庫資產足以覆蓋缺口再加上保證金 10% 時，才額外付給被爆倉的交易者
保證金的 10%。這是給交易者的安慰金，不是金庫的撥款上限；清算路徑沒有這筆。

### 2.2 清算

- 觸發條件：`平倉金額 ≤ 名目 × 維持保證金率`（預設 5%）。任何人都可以清算。
- 若剩餘抵押 > 0：清算人拿 5%，保險金庫拿 20%（清算罰金），其餘 75% 退回部位持有人的 `freeMargin`。
- 若剩餘抵押 ≤ 0：清算人拿 0，缺口走與 2.1 相同的「保險金庫 → ADL → 壞帳事件」。
- 清算依賴 oracle 價格新鮮度：價格超過 `maxPriceAge` 時，開倉、平倉與清算都會 revert。

### 2.3 誰吸收什麼（現行部署版）

| 順位 | 吸收者 | 吸收什麼 | 上限 |
|---|---|---|---|
| 1 | 虧損部位的持有人 | 該部位的保證金 | 保證金全額（逐倉，不跨部位） |
| 2 | 保險金庫 LP | 缺口 | 金庫總資產 |
| 3 | 反方向獲利部位的持有人 | 帳面獲利（被 haircut） | 被掃描到的獲利部位的獲利總和（最多 128 筆） |
| 4 | 資金池（間接由所有持有 `freeMargin` 的使用者承擔） | 未覆蓋壞帳 | 無上限；以 `BadDebt` 事件揭露 |

**結論**：現行部署版**不保證恆償付**。三層後盾都有上限，第四層是揭露而不是吸收。

## 3. 原始碼版（PR #191，未部署）新增了什麼

瀑布的順序不變，新增的是「讓瀑布更少被觸發」與「觸發時可以停下來」的控制：

| 控制 | 作用 | 預設 |
|---|---|---|
| 逐資產 OI 上限 | 開倉時以「數量 × 現價」檢查多空各自的未平倉量，超過就拒絕 | 關閉，由部署腳本設定 |
| 單筆獲利上限 | 開倉時凍結「保證金 × 倍數」（1×–25×）為該部位的獲利上限；平倉、清算與 ADL 都以截斷後的獲利結算 | 關閉，由部署腳本設定 |
| guardian 全域暫停 | guardian 或 owner 可暫停；只有 owner 能解除；guardian 的暫停 72 小時後自動失效，之後 24 小時冷卻 | 需在 cutover 時指定 guardian |
| 逐資產模式 | Active／**ReduceOnly**（禁止新開倉，可平倉與清算）／Halted（凍結該資產的開平倉、清算與 funding） | Active |
| 暫停後寬限期 | 暫停或 Halted 結束後 30 分鐘內禁止清算與開倉，並凍結暫停期間的 funding 與借貸費計息 | 固定 |
| mark 溢價上限 | 最多 200 bps | 固定上界 |
| 零價格 | 現行部署在寫入路徑（oracle 的 `updatePrice`）已經檢查；PR #191 把檢查延伸到讀取路徑（exchange 讀到零價格時 revert） | 固定 |
| 保險金庫 | 存入會得到 0 份額時 revert | 固定 |
| 跟單 slash 款項 | 改存 owner 持有的準備金，不進任何按份額分配的池子 | 固定 |

組合保證金（portfolio margin）：原始碼版在該模式下會先從帳戶的 `freeMargin` 扣缺口，但**沒有帳戶層級的
淨額清算**，PR #191 明文要求正式環境不得開啟，並規劃移除（移除是否完成以 PR 最終內容為準，本文**未驗證**）。

### 3.1 誰吸收什麼（原始碼版，逐倉）

| 順位 | 吸收者 | 與現行版的差異 |
|---|---|---|
| 0 | （事前）OI 上限、獲利上限、ReduceOnly、暫停 | 新增：限制資金池的最大曝險與單一贏家可主張的金額 |
| 1 | 虧損部位的持有人 | 相同 |
| 2 | 保險金庫 LP | 相同 |
| 3 | 反方向獲利部位 | 相同，但 haircut 以截斷後的獲利計算 |
| 4 | 壞帳事件 | 相同 |

**已知取捨**：全域暫停期間，提領、平倉與清算都會被擋下；guardian 可以用這個機制在一段期間內凍結出金。
細節見 [`KNOWN_LIMITATIONS.md`](KNOWN_LIMITATIONS.md)（PR #191 新增的第 21–25 項）。

## 4. 營運方可用的補救手段

- `InsuranceVault.recapitalize`（owner）：金庫在「資產為 0 但仍有份額」時會拒絕新存款，只能由 owner 注資恢復。
- 現行部署版**沒有**暫停或逐資產停單功能；原始碼版才有（見第 3 節）。緊急處置見
  [`INCIDENT_RESPONSE.md`](INCIDENT_RESPONSE.md)。

## 5. 代幣化配置金庫的非足額性質

`AssetVaultV2`（Base 現行為 2.4.0，proxy `0x916D7Fc399d9afd23BAa113E2c2Cc601341ff10a`）以 oracle 價格
mint／burn 合成資產代幣：

- **不是 1:1 USDC 準備**。金庫是每一個多頭的對手方；標的價格上漲時，負債隨之上升，準備可能不足。
- 限制曝險的機制（不是消除曝險）：
  - 最低準備率 `minReserveRatioBps`：現行 11000（110%）。低於門檻時拒絕新的 mint，**贖回不受此限**（避免擠兌）。
  - 逐資產曝險上限（`RISK_ROLE` 設定）。
  - mint 鎖（`mintingHalted`，見 `AssetVaultV2_4.sol` 的 `observeReserve` 與 `clearMintingHalt`）：
    - 由 `observeReserve()` 觸發：任何人呼叫時若準備率低於門檻，就鎖住 mint 並發出 `ReserveBreached`。
    - 自動清除：之後的 `observeReserve()` 發現準備率已回到門檻以上、**且所有資產都有報價**（沒有無法定價的資產）時，
      自動解除並發出 `ReserveRestored`。
    - 手動逃生口：`clearMintingHalt()`（`RISK_ROLE`）可在仍有資產無法定價時強制解除，發出 `MintingHaltCleared`；
      用於無法自動恢復的情況（例如某個資產的報價已永久停止）。
  - `PAUSER_ROLE` 可暫停。
  - mint 費率依碳分級，redeem 為固定費率。
- 準備不足時，贖回會因金庫沒有足夠 USDC 而失敗，持有人可能無法全額取回。
- 詳見 [`RISK_MODEL.md`](RISK_MODEL.md) 與 [`KNOWN_LIMITATIONS.md`](KNOWN_LIMITATIONS.md) 第 6 項。

## 6. 持牌客戶需要承擔或決定的部分（需客戶確認）

以下都不是合約能替客戶決定的事：

1. **負餘額保護政策**：逐倉下，合約本身不向交易者追討超過保證金的虧損。客戶要決定，對其終端客戶的承諾
   是否與此一致，以及 ADL 削減獲利、壞帳發生時如何對客戶揭露與處理。
2. **ADL 揭露**：終端客戶的帳面獲利可能被削減。客戶必須在契約與風險揭露書中寫明。
3. **壞帳補足**：`BadDebt` 事件發生後，是否由客戶以自有資金補足資金池，由客戶決定並載明。
4. **保險金庫資本**：由誰出資、規模、提領規則（現行沒有鎖倉期）。
5. **風險參數**：槓桿上限（例如依當地法規的散戶上限）、維持保證金、OI 與獲利上限、準備率門檻。
   原始碼版提供的上限預設關閉，必須由客戶的風險委員會設定。
6. **價格來源**：現行交易所讀取 keeper 寫入的預言機。客戶要決定是否接受這個信任假設，或要求改接授權的資料源。
7. **代幣化配置的準備**：誰負責在準備率下降時注資，以及無法贖回時對客戶的責任。

合規責任的完整分工見 [`COMPLIANCE_BOUNDARY.md`](COMPLIANCE_BOUNDARY.md)。
